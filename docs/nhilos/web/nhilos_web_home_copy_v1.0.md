## DATOS ESTRUCTURADOS JSON-LD (v1.3)

### Selección de tipos

| Tipo | Papel | ¿Por qué sí / por qué no otros |
|---|---|---|
| **`SoftwareApplication`** | El producto como software (con `applicationSubCategory: PointOfSale`) | Es el tipo que Google y los LLMs asocian a SaaS; permite `operatingSystem`, `featureList` y `offers`. Es el nodo principal |
| **`Organization`** | La entidad NHILOS (marca, contacto, redes, zona de servicio) | Sin `LocalBusiness`: ese tipo exige dirección física y NHILOS no tiene local; forzarlo genera inconsistencia en la ficha |
| **`FAQPage`** | Las 16 preguntas (6 humanas + 10 GEO) | Candidato a resultados enriquecidos y fuente directa para citas de LLMs |
| `WebSite` | Opcional, solo si se añade buscador del sitio (`SearchAction`) | No incluir ahora: sin página de búsqueda, `potentialAction` falso perjudica |
| `BreadcrumbList` | Solo en páginas internas (home no lo necesita) | Al construir las P0 |

**Reglas de integridad del schema (vinculantes):**

1. **Cero datos inventados:** sin `aggregateRating`, sin `review`, sin `offers.price` en el JSON-LD (la decisión v1.6 fue publicar precios solo como texto visible, no como datos estructurados de oferta).
2. **Sin dirección física** → el `Organization` lleva `areaServed` (Managua/Nicaragua) y `contactPoint`, no `address` postal.
3. **"Siempre abierto"** se declara como disponibilidad del servicio por WhatsApp/online (`hoursAvailable` 24/7 en el contactPoint), no como horario de un local.
4. `sameAs` enlaza las 3 redes con URL absoluta — es el hilo que conecta la ficha de entidad entre Google y los LLMs.
5. Todos los `@id` usan la base `https://www.nhilospos.com/#` para que los tres nodos queden enlazados entre sí (grafo, no fragmentos sueltos).
